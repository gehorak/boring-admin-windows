# AUDIT-EXPORT-FORMAT.md

Audit Export Format  
boring-admin-windows

---

## Purpose

This document defines the current **machine-readable audit export format**
for `boring-admin-windows v002`.

It exists to answer:

> What does `.\boring-admin.ps1 audit export` guarantee today?

This document is **operational guidance for the current export surface**.
It documents the present `v002` JSON shape.
It does not introduce a new authority layer or a future-state schema.

---

## Scope

This document describes only:

- the aggregate export shape produced by `.\boring-admin.ps1 audit export`
- the common fields returned by current verify scripts in JSON mode
- compatibility expectations for consumers of the export

This document does **not** define:

- storage location requirements
- retention policy
- archival tooling
- mandatory escrow or backup evidence fields
- a desired-state compliance schema

---

## Entry points

Windows-native:

```text
.\boring-admin.ps1 audit export
```

Make-based equivalent:

```text
make -f Makefile.audit audit-export
```

The output is intended for machine-readable consumption.

---

## Aggregate export shape

The current aggregate export is a JSON object with this top-level shape:

```json
{
  "scope": "audit-export",
  "generatedAt": "2026-04-01T12:00:00",
  "computerName": "WORKSTATION-01",
  "results": [
    {
      "scope": "security",
      "data": {}
    }
  ]
}
```

### Guaranteed top-level fields

- `scope`
  - current value: `audit-export`
- `generatedAt`
  - local timestamp string generated at export time
- `computerName`
  - current workstation name from the export environment
- `results`
  - array of per-scope audit results

---

## Results array

Each element of `results` currently has this shape:

```json
{
  "scope": "security",
  "data": {
    "scope": "security-visibility",
    "generatedAt": "2026-04-01T12:00:00",
    "warnings": []
  }
}
```

### Guaranteed result fields

- `scope`
  - aggregate scope label used by `boring-admin.ps1`
- `data`
  - parsed JSON object emitted by the underlying verify script

Current aggregate scopes are:

- `security`
- `software`
- `identity`
- `host`
- `system`
- `recovery`

The current aggregate ordering follows the current implementation order.
Consumers should not rely on ordering as the primary binding rule.
They should bind by `results[].scope`.

---

## Common per-scope JSON contract

Each verify script currently emits a scope-specific JSON object.

The common baseline shape is:

```json
{
  "scope": "scope-specific-name",
  "generatedAt": "2026-04-01T12:00:00",
  "warnings": []
}
```

### Common guaranteed fields

- `scope`
  - script-specific identifier for the emitted JSON object
- `generatedAt`
  - local timestamp string generated by the script
- `warnings`
  - array of warning messages
  - may be empty

### Common compatibility rule

Consumers may rely on:

- the presence of `scope`
- the presence of `generatedAt`
- the presence of `warnings`

Consumers must not assume:

- a fixed warning count
- fixed warning message wording forever
- that warnings imply failure

In `v002`, verify scripts follow the read-only `Variant A` exit model:

- exit `0` on completed verification, with or without warnings
- exit `1` only on fatal error

---

## Current domain sections

The `data` object contains a domain-specific section in addition to the common fields.

Current domain sections are:

- security -> `security`
- software -> `inventory` and `packageManager`
- identity -> `identity`
- host -> `host`
- system -> `system`
- recovery -> `recovery`

These sections are current `v002` behavior,
not a promise that all future versions will keep identical subfield naming forever.

---

## Current examples

### Security

Current security export includes:

- `security.windowsDefender`
- `security.firewallProfiles`
- `security.bitLockerVolumes`
- `security.secureBootEnabled`

### Software

Current software export includes:

- `packageManager.chocolatey`
- `packageManager.winget`
- `inventory.uninstallEntryCount`
- `inventory.markers`

### Identity

Current identity export includes:

- `identity.localUsers`
- `identity.administratorsGroup`
- `identity.managedAccounts`
- `identity.disabledAdministrators`

### Host

Current host export includes:

- `host.computerName`
- `host.timeZone`
- `host.systemLocale`

### System

Current system export includes:

- `system.os`
- `system.computer`
- `system.administrators`
- `system.defender`
- `system.firewall`
- `system.bitLocker`
- `system.policyMarkers`
- `system.chocolatey`
- `system.temporaryAccessAccount`

### Recovery

Current recovery export includes:

- `recovery.recoveryAdministrator`
- `recovery.bitLockerVolumes`
- `recovery.externalChecklist`

Important limitation:

Current recovery export does **not** prove:

- actual external key escrow success
- backup success
- restore success
- secret retrieval success

It only reports current `v002` recovery visibility signals.

## Optional and unstable details

Consumers should treat these as optional or version-sensitive:

- exact nested field set inside each domain section
- exact warning message text
- ordering of arrays
- ordering of top-level `results`

Consumers should prefer:

- checking presence of a field before relying on it
- binding to `scope`
- treating unknown additional fields as non-breaking

---

## Compatibility rules

### Stable enough to depend on in v002

- aggregate wrapper with `scope`, `generatedAt`, `computerName`, `results`
- per-result `scope` and `data`
- per-scope `scope`, `generatedAt`, `warnings`
- current domain scope names in aggregate export

### Not guaranteed as frozen public schema

- exact nested data model of every domain section
- semantic meaning of every warning string
- permanent existence of every optional subfield

This is a practical `v002` contract,
not a versioned enterprise schema registry.

---

## Non-goals

This document does **not** declare:

- a compliance model
- a policy enforcement model
- escrow verification claims
- archive directory layout
- mandatory import integration with other systems

Those concerns are outside current `v002` scope.
